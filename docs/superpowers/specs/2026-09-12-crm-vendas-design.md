# CRM de vendas (item 24, parte 3) — design

Status: aprovado para implementação
Data: 2026-09-12

Pedido do usuário: pipeline de leads/vendas do SaaS, visível só pro
ADM (nunca pra profissional/paciente). Partes 1 (e-mail ao ADM) e 2
(rastreamento de visita) já implementadas. Esta parte constrói o
schema e a tela.

## Decisões já tomadas com o usuário

- Toda conta nova (`Usuarios`) gera um Lead automaticamente, além de
  leads manuais que o ADM cadastra à mão.
- Estágios fixos (não editável pelo admin nesta v1): `novo`,
  `em_contato`, `qualificado`, `proposta_enviada`, `fechado_ganho`,
  `perdido`.
- Cada lead tem notas com timestamp (histórico de interação).
- Tela de lista simples com filtro por estágio + dropdown pra mudar
  estágio — sem Kanban/drag-and-drop (nenhuma dependência desse tipo
  existe no projeto hoje).

## O que já existe (não faz parte desta entrega)

- `/admin/leads` — lista somente-leitura de psicólogos raspados do
  registro público do CFP (`leads_cfp`, sem RLS, sem estágio/contato/
  nota — é referência estática, não pipeline de vendas). **Renomeada
  pra `/admin/leads-cfp` nesta entrega** — a URL `/admin/leads` passa a
  ser do CRM novo, por ser o uso mais frequente daqui pra frente.
- `public.is_admin()` (`supabase/migrations/20260727000003...`) —
  helper já usado em outras tabelas admin-only (`ClassificacaoFinanceira`,
  policy de escrita de `artigos`) — reaproveitado aqui como o predicado
  de RLS.
- `web/lib/actions/auth.js` (`cadastrar()`) — ganha a criação
  automática do Lead.
- `web/lib/supabase/admin.js` (`createAdminClient()`) — usado pra criar
  o Lead automático (o novo usuário, recém-criado, não é admin, então
  a policy RLS do Lead bloquearia esse insert pela sessão dele mesmo;
  o insert automático roda com service-role, mesmo raciocínio já usado
  no webhook do Asaas).

## Schema

```sql
create table "Lead" (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  atualizado_em timestamptz not null default now(),
  nome text not null,
  telefone text,
  email text,
  usuario_id bigint references "Usuarios"(id),
  visitante_sessao_id uuid,
  estagio text not null default 'novo'
    check (estagio in ('novo', 'em_contato', 'qualificado', 'proposta_enviada', 'fechado_ganho', 'perdido')),
  origem text not null default 'manual' check (origem in ('cadastro', 'manual'))
);

create table "LeadNota" (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  lead_id bigint not null references "Lead"(id) on delete cascade,
  texto text not null
);

alter table "Lead" enable row level security;
alter table "LeadNota" enable row level security;

create policy "lead_admin_all" on "Lead"
  for all using (public.is_admin()) with check (public.is_admin());
create policy "leadnota_admin_all" on "LeadNota"
  for all using (public.is_admin()) with check (public.is_admin());
```

Sem FK entre `Lead.visitante_sessao_id` e `VisitaPagina.sessao_id` —
mesmo raciocínio já documentado pra `Usuarios.visitante_sessao_id`
(não é chave única, o link é só por igualdade de valor na consulta).

`origem` só tem `cadastro`/`manual` nesta entrega — `whatsapp` (parte 4,
ainda não construída) entra como migration própria quando aquela parte
existir, mesmo padrão incremental já usado no projeto (ex.:
`codigo_tributacao_municipal` adicionado depois, sob demanda).

## Criação automática em `cadastrar()`

Depois do insert em `Usuarios` (que passa a usar `.select("id").single()`
pra ter o id de volta), insere em `Lead` via `createAdminClient()`:
`nome`, `telefone` (mesmo valor de `contato`), `email`,
`usuario_id`, `visitante_sessao_id` (o mesmo cookie já lido pro item
24/2), `estagio: "novo"`, `origem: "cadastro"`. Melhor esforço — não
bloqueia o cadastro se falhar (mesmo padrão dos outros efeitos
colaterais dessa função).

## Camada de dados e ações

- `web/lib/data/crm.js` (novo, separado de `web/lib/data/leads.js` que
  já existe pros leads do CFP — são conceitos diferentes, não
  misturar): `listarLeads({ estagio })`, `buscarLead(id)` (com notas
  aninhadas via join).
- `web/lib/actions/crm.js` (novo): `criarLeadManual(prevState,
  formData)`, `atualizarEstagioLead(leadId, novoEstagio)`,
  `adicionarNotaLead(leadId, prevState, formData)`. Todas usam o
  client autenticado normal (`createClient()`) — a RLS
  `public.is_admin()` já garante que só admin escreve; a página
  também confere `role === "admin"` antes de renderizar, mesmo padrão
  de `/admin/leads-cfp` e `/admin/artigos`.

## Telas

- **`web/app/(app)/admin/leads-cfp/`** — pasta movida de
  `web/app/(app)/admin/leads/` (conteúdo idêntico, só o caminho muda).
- **`web/app/(app)/admin/leads/page.js`** (novo, CRM): lista de leads,
  filtro por estágio (querystring `?estagio=`, default mostra todos),
  cada linha com nome/telefone/origem/data e um `<select>` de estágio
  que já dispara `atualizarEstagioLead` no `onChange` (client
  component pequeno, sem precisar de botão "salvar" separado). Link
  pro nome leva pro detalhe. Formulário "Novo lead" no topo (nome +
  telefone, campos mínimos).
- **`web/app/(app)/admin/leads/[id]/page.js`** (novo): dados do lead,
  lista de notas (mais recente primeiro) e formulário pra adicionar
  nota nova.
- `web/app/(app)/admin/layout.js` — link de nav "Leads CFP" atualiza
  pra `/admin/leads-cfp`; novo link "CRM" (ou "Leads") pra
  `/admin/leads`.
