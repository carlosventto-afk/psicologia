# Item 7 do backlog — Emissão de NFS-e direto pelo sistema

**Status:** aprovado, pronto para implementação.

## Objetivo

Pra pacientes marcados como "Nota Fiscal" (`Paciente.documento = 'nota_fiscal'`,
item 6, já implementado), emitir NFS-e no padrão Nacional (SEFIN/gov.br)
direto pelo sistema, sem sair do app, e enviar automaticamente por e-mail
ao paciente assim que a nota for autorizada.

Depende do item 6, já implementado.

## Contexto e decisões já fechadas

- **Licenciamento**: o kit usado (`NotaFiscal/nfse-nacional-kit`, extraído
  de um ERP em produção da TN Costa Tecnologia) não declara licença
  aberta — foi compartilhado diretamente com o usuário pelo autor. O
  usuário confirmou que os termos de uso dentro do PsiAgente já estão
  liberados diretamente com o autor. Não é mais um bloqueio.
- **Self-service completo**: qualquer profissional cadastrado no PsiAgente
  pode emitir NFS-e, preenchendo os próprios dados fiscais numa tela nova
  — não é uma feature restrita a um profissional específico nem
  administrada por um admin da plataforma.
- **Ambiente (homologação/produção)**: todo profissional novo começa em
  **homologação** (produção restrita da Receita — não gera documento
  fiscal real). A troca pra **produção** é feita pelo próprio profissional
  na tela de configurações fiscais, com um aviso explícito de que é
  **irreversível** antes de confirmar. Depois de trocar pra produção, o
  sistema não permite voltar pra homologação — decisão do usuário, pra
  evitar alternância acidental.
- **PDF (DANFSe)**: sem gerador de PDF próprio nesta v1. O PDF oficial vem
  de uma API separada (ADN) que o próprio kit avisa que cai com
  frequência. Se estiver indisponível no momento da emissão, a nota fica
  autorizada normalmente (o XML é gravado — é o documento fiscal válido,
  o PDF é só representação) e a tela oferece "Tentar baixar PDF" pra
  repetir depois.
- **Cancelamento**: incluído nesta v1 (o kit já suporta, e é a saída de
  emergência se uma nota for emitida errada).

## Arquitetura: microserviço Python

O kit (`nfse_core/`) é Python puro, sem framework web, com armadilhas
delicadas já medidas contra o validador real da SEFIN (canonicalização
XML, assinatura RSA-SHA1 manual, ordem de campos — ver
`docs/ARMADILHAS.md` do kit). Reescrever essa lógica em JS arriscaria
reintroduzir bugs que já custaram dias pra descobrir, sem ganho real.

Solução: um **microserviço Python novo** (`psiagente-nfse`, FastAPI),
container próprio no EasyPanel, na mesma VPS onde já rodam o app principal
e o Evolution API (mesmo padrão de infra — ver memória
`psifacil-deploy-infra`). Endpoints internos:

- `POST /certificado/validar` — recebe `.pfx` (base64) + senha, confere
  titularidade/validade (`nfse_core.certificado.inspecionar`), cifra com
  Fernet (chave dedicada, variável de ambiente só deste serviço) e devolve
  o blob cifrado + titular + CNPJ/CPF + data de validade. Nunca grava nada
  em disco.
- `POST /emitir` — recebe os dados fiscais do profissional (já
  descriptografando o blob do certificado internamente), dados do
  paciente/valor, monta a DPS, assina, envia à SEFIN, devolve o resultado
  (autorizada + chave/XML, ou rejeitada + erros traduzidos).
- `POST /cancelar` — idem, pro evento de cancelamento (e101101).
- `GET /consultar` — consulta por chave/DPS, saída de emergência se uma
  resposta se perder no meio do caminho.

Autenticação: header com segredo compartilhado (`NFSE_SERVICE_SECRET`),
mesmo padrão já usado em `/carne-leao-automatico` — sem o header correto,
`401` imediato. O serviço só é alcançável dentro da rede interna do
EasyPanel, nunca exposto como rota pública.

**Por que toda operação de certificado passa pelo Python, nunca pelo
Node**: o `.pfx` e a senha nunca ficam em texto puro em nenhum ponto do
Next.js/Node. O Node só guarda e repassa o blob já cifrado; quem cifra e
decifra é sempre o microserviço, que já usa `cryptography` pra isso.

## Modelo de dados

Duas tabelas novas no Supabase:

```sql
create table "DadosFiscaisProfissional" (
  id bigint generated by default as identity primary key,
  usuario bigint not null unique references "Usuarios"(id),

  -- Emitente (Parte 2 da spec, campos conferidos contra a DANFSe real)
  tipo_documento text not null check (tipo_documento in ('cpf', 'cnpj')),
  documento text not null,
  inscricao_municipal text,
  nome_empresarial text not null,
  email_nfse text not null,
  telefone_nfse text,
  logradouro text not null,
  numero text not null,
  complemento text,
  bairro text not null,
  municipio_ibge text not null,        -- codigo IBGE, 7 digitos
  uf text not null,
  cep text not null,

  -- Regime tributario
  optante_simples_nacional int not null default 3
    check (optante_simples_nacional in (1, 2, 3)), -- 1=nao optante, 2=MEI, 3=ME/EPP
  regime_apuracao_sn int,              -- obrigatorio quando optante_simples_nacional=3

  -- Servico
  codigo_tributacao_nacional text not null, -- LC116, preenchido pelo profissional

  -- Certificado (cifrado, nunca em texto puro)
  certificado_pfx_cifrado text,
  certificado_senha_cifrada text,
  certificado_titular text,
  certificado_validade date,

  -- Controle
  ambiente text not null default 'homologacao' check (ambiente in ('homologacao', 'producao')),
  serie text not null default '1',
  proximo_numero int not null default 1,

  created_at timestamptz not null default now()
);

create table "NotaFiscal" (
  id bigint generated by default as identity primary key,
  owner uuid not null references auth.users(id),
  pagamento_sessao bigint not null unique references "PagamentoSessao"(id),

  status text not null default 'pendente'
    check (status in ('pendente', 'autorizada', 'rejeitada', 'cancelada')),
  ambiente text not null,
  numero int not null,
  serie text not null,
  dps_id text,
  chave_acesso text,
  xml_dps text,
  xml_nfse text,
  erros jsonb,

  created_at timestamptz not null default now()
);
```

**Correção em relação à primeira versão desta spec**: `NotaFiscal` referencia
`PagamentoSessao`, não `Sessao` diretamente. Conferindo o código do item 8
(Carnê-Leão) durante o planejamento, o valor real de uma sessão pra fins
fiscais é o que está registrado em `PagamentoSessao.valor`/`data_pagamento`
(o que foi de fato recebido), não `Sessao`/`Paciente.valor_sessao` (o preço
nominal) — `/recibos` (item 6) usa o preço nominal, mas isso é uma
simplificação daquele item específico que não deve se repetir aqui: emitir
um documento fiscal com o valor nominal em vez do valor realmente pago é
uma inconsistência fiscal real. `NotaFiscal.pagamento_sessao` é `unique`
pra impedir duas notas pro mesmo pagamento. Diferente do item 8, esta v1
**não** tem a opção de combinar múltiplos pagamentos numa nota só — é
sempre 1 nota por `PagamentoSessao` (YAGNI: essa combinação é um recurso a
mais que pode entrar depois, se pedido).

- `DadosFiscaisProfissional.codigo_tributacao_nacional` é **preenchido
  pelo próprio profissional** (ou pelo contador dele) — o kit tem um
  default (`"080101"`, item de serviços educacionais) que não serve pra
  psicologia; o código certo (LC 116) varia e um valor errado é problema
  fiscal real, então não fixamos nenhum padrão.
- `NotaFiscal.status = 'pendente'` é gravado **antes** de chamar o
  microserviço (mesmo padrão recomendado em `docs/INTEGRACAO.md` do kit)
  — se o processo cair no meio, sobra um registro pendente com o `dps_id`
  pra consultar depois, em vez de a nota existir na SEFIN e não existir no
  app.
- RLS: `DadosFiscaisProfissional` e `NotaFiscal` seguem o mesmo padrão do
  resto do sistema — cada profissional só vê/edita os próprios registros
  (`owner = auth.uid()` / join por `usuario`).

## Numeração transacional

`proximo_numero` é incrementado dentro da mesma transação da emissão, com
`UPDATE ... RETURNING` (trava a linha, serializa emissões concorrentes do
mesmo profissional) — nunca lido com `SELECT` separado antes de gravar,
que é o caminho da duplicata segundo o próprio kit.

Se a SEFIN rejeitar a nota, o número já foi consumido e **não é
reciclado** — o padrão fiscal aceita buracos na sequência.

## Telas e fluxo de emissão

- **`/configuracoes/nfse`** (nova aba, ao lado de `/configuracoes/conta`):
  formulário com os dados de `DadosFiscaisProfissional`, upload do
  certificado (chama `/certificado/validar` no microserviço antes de
  gravar, rejeitando arquivo/senha errados na hora), banner de alerta
  quando o certificado estiver perto de vencer, e o botão de troca
  homologação→produção com o aviso de irreversibilidade.
- **`/notas-fiscais`** (mais parecido com a fonte de dados do `/carne-leao`
  — item 8 — do que com `/recibos`): lista **pagamentos**
  (`PagamentoSessao`) de sessões de pacientes com
  `Paciente.documento = 'nota_fiscal'` que ainda não têm `NotaFiscal`
  associada, com botão "Emitir nota fiscal" por linha. Emissão é
  **síncrona** (uma nota por clique) — não precisa de fila/job em lote
  nesta v1, diferente do Carnê-Leão (que processa muitos pagamentos de
  uma vez).
- Ao autorizar: e-mail automático pro paciente. **Correção em relação à
  primeira versão desta spec**: o item 9 (Carnê-Leão) não tem nenhum envio
  de e-mail dentro do app — quem manda lá é um n8n externo, que ainda nem
  está implantado em produção. Não há infra de e-mail reaproveitável.
  Este item introduz a primeira: um helper `sendEmail` no próprio Next.js
  chamando a API HTTP do **Resend** (nova env var `RESEND_API_KEY`),
  mandando o XML anexado (documento fiscal válido) e o PDF quando
  disponível na hora — sem depender do n8n, que segue fora de escopo.
- **Cancelamento**: botão "Cancelar nota" na lista de notas emitidas,
  chama `/cancelar` no microserviço. Sujeito ao prazo/regras do
  município — se a SEFIN rejeitar por prazo vencido, o erro traduzido
  (`error_catalog.py` do kit) aparece na tela.
- **Erros de emissão**: sempre traduzidos via `error_catalog.py` do kit
  antes de chegar na tela — o operador nunca vê um código cru da SEFIN
  sem explicação.

## Fora de escopo desta v1

- Emissão em lote (múltiplas notas de uma vez) — cada nota é emitida
  individualmente, pelo operador.
- Gerador de PDF próprio como fallback da API do ADN — se ela estiver
  fora do ar, o operador tenta baixar de novo depois; o XML já está
  seguro.
- Campos da reforma tributária (IBS/CBS) — o próprio kit já isola isso
  pra uma fase 2, quando o validador da produção restrita estabilizar o
  leiaute novo.
- Edição de `DadosFiscaisProfissional` depois de já existir alguma
  `NotaFiscal` emitida — nesta v1 o formulário permanece editável
  livremente; travar campos específicos (ex: CNPJ, município) depois da
  primeira emissão fica pra uma iteração futura, se necessário.
- Múltiplos certificados/CNPJs por profissional — assume-se um emitente
  só por profissional.

## Decisões em aberto pra implementação

Não bloqueiam o design, mas precisam ser resolvidas durante a construção,
contra o manual oficial (`gov.br/nfse`) e/ou a produção restrita:

- Valores exatos do enum `regime_apuracao_sn` (regime de apuração do
  Simples Nacional) conforme a tabela oficial do leiaute — conferir antes
  de implementar o select da tela.
- `municipio_ibge`: nesta v1, campo de texto livre validado por formato
  (7 dígitos), sem uma base de municípios pra busca por nome — mais
  simples, sem precisar manter uma tabela de referência no sistema.
- Nome final da env var do segredo compartilhado
  (`NFSE_SERVICE_SECRET` sugerido, mesmo padrão de
  `CARNE_LEAO_CRON_SECRET`) e da chave de cifra do certificado
  (`NFSE_CERT_ENCRYPTION_KEY`), ambas só no microserviço Python.
- `RESEND_API_KEY` (Next.js) — conta Resend nova a criar; remetente
  (domínio verificado) a definir na hora da implementação.
- Implantação do serviço `psiagente-nfse` no EasyPanel (novo Dockerfile,
  novo container) é trabalho de infraestrutura que acontece junto da
  implementação, não antes — diferente do item 9, aqui o serviço faz
  parte do próprio código deste item, não é uma dependência externa a
  configurar depois.
