# Fallback de e-mail + resumo diário por WhatsApp — design

Status: aprovado para implementação
Data: 2026-09-12

Pedido do usuário: hoje `enviarEmailResend` falha silenciosamente em
todo lugar que a chama (cadastro, contrato fechado, escalação de lead,
link mágico) — sem fila de reenvio, sem aviso. Pedido: fila de reenvio
automático, aviso pro gestor quando esgotar as tentativas, e um resumo
diário por WhatsApp do que aconteceu no CRM.

## Decisões já tomadas com o usuário

- Fallback é só sobre **e-mail** (não WhatsApp).
- Aviso só quando a fila **esgota as tentativas** (falha definitiva),
  não a cada falha isolada.
- Resumo diário e aviso de fila esgotada vão por **WhatsApp** pro
  número do gestor: `(91) 98191-0295` (mesmo número já usado como
  contato comercial na home — `+55 91 98191-0295`).

## O que já existe (reaproveitado, não muda)

- `web/lib/email/resend.js` (`enviarEmailResend`, `EMAIL_ADMIN`) —
  ganha enfileiramento automático na falha, sem mudar a assinatura
  nem nenhum dos ~5 call sites atuais.
- Padrão de rota de cron autenticada por segredo compartilhado
  (`web/app/api/assinaturas/aplicar-pendencias/route.js`) — mesmo
  modelo pras 2 rotas novas.
- `web/lib/supabase/proxy.js` (`PUBLIC_PATHS`) — as 2 rotas novas
  precisam entrar aqui, senão o middleware bloqueia antes de rodar
  (lição já registrada nesta mesma sessão, mais de uma vez).
- Evolution API (`https://psifacil-evolution-api.lcuzxl.easypanel.host`,
  instância `psifacil`) — hoje só o n8n manda mensagem por ela
  ("WA - Enviar Mensagem"); o Next.js ganha um cliente próprio pra
  avisos administrativos que não pertencem a uma conversa de lead.
- n8n Schedule Trigger — mesmo padrão já em produção
  ("Assinaturas - Aplicar Pendencias (diario)", dispara via
  `httpRequest` com credencial de header).

## Schema

```sql
create table "EmailFalhado" (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  destinatario text not null,
  assunto text not null,
  corpo_html text not null,
  tentativas int not null default 0,
  proxima_tentativa timestamptz not null default now(),
  resolvido boolean not null default false,
  esgotado boolean not null default false,
  ultimo_erro text
);

alter table "EmailFalhado" enable row level security;
-- sem policy: só service_role lê/escreve, mesmo padrão de
-- "EventoAssinatura"/"EnvioAutomaticoCarneLeao".
```

## `enviarEmailResend` — enfileiramento automático

Continua com a mesma assinatura (`{to, subject, html}` → `{error}`).
Na falha (rede OU resposta não-ok do Resend), além de retornar
`{error}` como já faz, insere uma linha em `EmailFalhado`
(`tentativas: 0`, `proxima_tentativa: now()`). Todo call site atual
continua funcionando sem alteração — o fallback é transparente.

## Backoff

5 tentativas, intervalos crescentes a partir de quando a tentativa
anterior falhou: 5min → 30min → 2h → 12h → 24h. Na 5ª falha, marca
`esgotado = true` e dispara o aviso por WhatsApp (não tenta mais depois
disso — reprocessamento manual seria via UPDATE direto, fora de escopo
desta entrega).

## Rota: `POST /api/emails/reprocessar-fila`

Mesmo padrão de segredo compartilhado (`x-cron-secret`, env var
`EMAIL_QUEUE_CRON_SECRET`). Busca `EmailFalhado` com `resolvido = false
and esgotado = false and proxima_tentativa <= now()`, tenta reenviar
cada um chamando a API do Resend direto (não via `enviarEmailResend`,
pra não enfileirar de novo o mesmo e-mail em cima do que já está na
fila). Sucesso: `resolvido = true`. Falha: incrementa `tentativas`,
recalcula `proxima_tentativa` pelo array de backoff, ou marca
`esgotado = true` (+ dispara WhatsApp) se já era a 5ª.

```js
export const NUMERO_GESTOR = "5591981910295";

```

Mesmo formato de request que "WA - Enviar Mensagem" do n8n já usa
(`POST /message/sendText/psifacil`, header `apikey`, body
`{number, text}`) — replicado aqui porque é chamada administrativa
direta, sem passar por um workflow do n8n. Precisa de
`EVOLUTION_API_KEY` novo em produção (mesmo valor já configurado no
serviço da Evolution API — `AUTHENTICATION_API_KEY` do serviço
`evolution-api`).

## Rota: `POST /api/relatorios/resumo-diario`

Mesmo padrão de segredo (`RESUMO_DIARIO_CRON_SECRET`). Monta e manda
via `enviarWhatsapp` pro `NUMERO_GESTOR`: quantidade de leads criados
nas últimas 24h (por origem), quantos estão com `aguardando_humano =
true` agora, e quantos e-mails na fila (pendente vs. esgotado nas
últimas 24h).

## n8n

Dois Schedule Trigger novos, mesmo modelo de
"Assinaturas - Aplicar Pendencias (diario)": um a cada 15min chamando
`/api/emails/reprocessar-fila`, um diário às 9h chamando
`/api/relatorios/resumo-diario`. Cada um com sua própria credencial de
header (`httpHeaderAuth`), mesmo padrão das credenciais de cron já
existentes.

## Testes

Sem framework automatizado. Verificação por camadas com dado
descartável: migration aplicada; forçar uma falha de envio (destinatário
inválido) e confirmar linha em `EmailFalhado`; chamar
`/api/emails/reprocessar-fila` direto via curl com o segredo certo,
confirmar `tentativas`/`proxima_tentativa` avançando; simular as 5
tentativas (ajustando `proxima_tentativa` direto no banco pra não
esperar o backoff de verdade) e confirmar que a 5ª marca `esgotado` e
manda WhatsApp de teste pro número do gestor; chamar
`/api/relatorios/resumo-diario` direto via curl, confirmar conteúdo e
entrega. Apagar todo dado de teste ao final.
