# Agente de WhatsApp — RPCs novas (Parte A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adicionar as 5 RPCs novas do agente de WhatsApp (reagendar sessão com contador/alerta, excluir sessão, excluir pagamento, registrar lançamento de despesa, registrar item de anamnese) + a tabela `SessaoReagendamento`, seguindo exatamente o padrão de segurança/estrutura das 11 RPCs já existentes.

**Architecture:** Cada RPC é `security definer`, primeiro parâmetro `p_whatsapp_number text`, resolve o profissional/consultório via as funções helper já existentes (`_agent_get_owner_uuid`, `_agent_resolve_consultorio`), e só é executável pela `service_role` (nunca `anon`/`authenticated`). Cada tool novo é uma migration própria, aplicada e verificada com dados descartáveis contra produção — mesmo padrão usado no item 12 (Anamnese).

**Tech Stack:** Supabase Postgres (PL/pgSQL, RLS), scripts Node ad-hoc (`pg`/`@supabase/supabase-js`) pra aplicar/verificar migrations — mesmo padrão de todos os planos anteriores deste projeto.

**Spec:** `docs/superpowers/specs/2026-08-17-agente-whatsapp-profissional-design.md`

**Fora deste plano:** o workflow n8n (`WA - Inbound Router` + `WA - Agent Psicólogo`) que efetivamente liga o WhatsApp a essas tools via um LLM. Essa parte não é escrita como diff de arquivo (é construída numa ferramenta visual) e depende de decisões operacionais ainda não levantadas (acesso à API do n8n, onde fica a credencial do Claude, testes reais com mensagem de WhatsApp) — vira um plano/brainstorm próprio depois que esta parte (as tools em si) estiver pronta e revisada.

## Global Constraints

- Toda função nova segue o padrão de `supabase/migrations/20260727000002_create_agent_rpc_functions.sql`: `language plpgsql security definer set search_path = public`, primeiro parâmetro `p_whatsapp_number text`, chama `public._agent_resolve_consultorio(p_whatsapp_number, p_consultorio_id)` pra resolver/validar o consultório antes de qualquer outra coisa.
- Toda função termina com `revoke all on function ... from public, anon, authenticated;` seguido de `grant execute on function ... to service_role;` — nunca deixar uma função nova sem essas duas linhas.
- Convenção de valores de texto confirmada em produção (migration `20260727000005_fix_text_casing.sql`): `Sessao.status` = `'Marcada'` | `'Realizada'` | `'Cancelada'` (capitalizado); `LancamentoFinanceiro.tipo` = `'Receita'` | `'Despesa'` (capitalizado). Nunca usar a versão minúscula.
- Erros de negócio são sempre `raise exception '<CODIGO_EM_MAIUSCULO>' using errcode = 'P0001';` — mesmo padrão das 11 tools existentes (nunca mensagem solta, sempre um código que o n8n possa capturar).
- `agent_reagendar_sessao` só aceita sessões com `"Realizado" = false and status is distinct from 'Cancelada'` (o `is distinct from` trata `status` nulo como reagendável, mesmo padrão defensivo já usado no Painel pra dados legados).
- O limiar de alerta de reagendamento é **3 no mês corrente**, hardcoded na função (sem UI de configuração nesta entrega).
- Qualquer dado de teste (paciente/sessão/pagamento/usuário) criado durante verificação é descartável e apagado ao final do próprio script — nunca deixar lixo em produção.
- Conexão Postgres direta: `postgresql://postgres:<SUPABASE_DB_PASSWORD>@db.rohulajgyxdangxfurha.supabase.co:5432/postgres` (`SUPABASE_DB_PASSWORD` já disponível no ambiente). `.env.local` em `web/` tem `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` pros scripts que usam `@supabase/supabase-js`.

## Task 2: RPC `agent_reagendar_sessao`

**Files:**
- Create: `supabase/migrations/20260817000002_add_agent_reagendar_sessao.sql`

**Interfaces:**
- Consumes: `SessaoReagendamento` (Task 1), `_agent_resolve_consultorio` (já existe).
- Produces: `agent_reagendar_sessao(p_whatsapp_number text, p_sessao_id bigint, p_data_nova date, p_horario_novo time, p_consultorio_id bigint default null) returns jsonb` — retorna `{ sessao_id, reagendamentos_mes_atual, alerta }`.

- [ ] **Step 1: Escrever a migration**

```sql
create or replace function public.agent_reagendar_sessao(
  p_whatsapp_number text,
  p_sessao_id bigint,
  p_data_nova date,
  p_horario_novo time,
  p_consultorio_id bigint default null
)
returns jsonb
language plpgsql
security definer
set search_path = public
as $$
declare
  v_consultorio_id bigint;
  v_paciente_id bigint;
  v_data_anterior date;
  v_horario_anterior time;
  v_reagendamentos_mes int;
begin
  v_consultorio_id := public._agent_resolve_consultorio(p_whatsapp_number, p_consultorio_id);

  select s.paciente, s.data, s.horario
    into v_paciente_id, v_data_anterior, v_horario_anterior
  from "Sessao" s
  join "Paciente" p on p.id = s.paciente
  where s.id = p_sessao_id
    and p.consultorio = v_consultorio_id
    and s."Realizado" = false
    and s.status is distinct from 'Cancelada';

  if v_paciente_id is null then
    raise exception 'SESSAO_NAO_REAGENDAVEL' using errcode = 'P0001';
  end if;

  update "Sessao"
  set data = p_data_nova, horario = p_horario_novo
  where id = p_sessao_id;

  insert into "SessaoReagendamento" (sessao, paciente, data_anterior, horario_anterior, data_nova, horario_novo)
  values (p_sessao_id, v_paciente_id, v_data_anterior, v_horario_anterior, p_data_nova, p_horario_novo);

  select count(*) into v_reagendamentos_mes
  from "SessaoReagendamento"
  where paciente = v_paciente_id
    and reagendado_em >= date_trunc('month', now())
    and reagendado_em < date_trunc('month', now()) + interval '1 month';

  return jsonb_build_object(
    'sessao_id', p_sessao_id,
    'reagendamentos_mes_atual', v_reagendamentos_mes,
    'alerta', v_reagendamentos_mes >= 3
  );
end;
$$;

revoke all on function public.agent_reagendar_sessao(text, bigint, date, time, bigint) from public, anon, authenticated;
grant execute on function public.agent_reagendar_sessao(text, bigint, date, time, bigint) to service_role;
```

## Task 3: RPC `agent_excluir_sessao`

**Interfaces:**

- [ ] **Step 1: Escrever a migration**

```sql
create or replace function public.agent_excluir_sessao(
  p_whatsapp_number text,
  p_sessao_id bigint,
  p_consultorio_id bigint default null
)
returns boolean
language plpgsql
security definer
set search_path = public
as $$
declare
  v_consultorio_id bigint;
begin
  v_consultorio_id := public._agent_resolve_consultorio(p_whatsapp_number, p_consultorio_id);

  delete from "Sessao" s
  where s.id = p_sessao_id
    and exists (
      select 1 from "Paciente" p
      where p.id = s.paciente and p.consultorio = v_consultorio_id
    );

  if not found then
    raise exception 'SESSAO_NAO_ENCONTRADA' using errcode = 'P0001';
  end if;

  return true;
exception
  when foreign_key_violation then
    raise exception 'SESSAO_TEM_VINCULO_FINANCEIRO' using errcode = 'P0001';
end;
$$;

revoke all on function public.agent_excluir_sessao(text, bigint, bigint) from public, anon, authenticated;
grant execute on function public.agent_excluir_sessao(text, bigint, bigint) to service_role;
```
